# HydraScript

**A Pythonic syntax for React, compiled by a native Rust binary.**

[![npm](https://img.shields.io/npm/v/hydrascript.svg)](https://www.npmjs.com/package/hydrascript)
[![license](https://img.shields.io/npm/l/hydrascript.svg)](LICENSE)

[npm](https://www.npmjs.com/package/hydrascript) | [English](README.md) | [Bahasa Indonesia](README.id.md)

---

## What this is

HydraScript compiles indentation-based `.hyx` files to React TSX and `.hys` files
to plain JavaScript. The compiler is a Rust binary; a small Node runner wraps
esbuild, PostCSS and Tailwind to produce a site.

**Status: 0.15.0, pre-1.0.** The compiler, file-based router, prerendering,
server rendering, language server, Fast Refresh, and test runner are implemented
and covered by 418 Rust tests (281 unit + 137 integration) and 221 Node tests
across 27 suites. The language syntax is frozen (see below); what ships between
now and 1.0 is polish and production hardening, not new constructs.

All roadmap targets are shipped — see [Roadmap](#roadmap).

### The syntax is frozen at 0.3

No new language features are planned before 1.0. That is a decision, not
inertia: a small language earns trust by standing still long enough for people
to build on it, and every added construct is an emitter path to maintain
forever. What changes between now and 1.0 is plumbing, not syntax: the build,
the dev server, diagnostics, bundler integration, CI, and type declarations. If
an idea needs new syntax, the answer is almost always no.

Breaking changes still happen, and every one of them carries a codemod or a
migration note. No exceptions, even with few users: projects die because people
stop daring to upgrade, not because of missing features.

## A 30-second example

```python
# [xihanzu-NR]
from hydra import state

component Counter(start: int = 0):
    count, set_count = state(start)

    div(className="counter"):
        h2: f"Value: {count}"
        button(onClick=lambda: set_count(count + 1)): "Add"
```

compiles to (verbatim compiler output, base64 source-map footer trimmed):

```tsx
// [xihanzu-NR]
// GENERATED by hydra — edit the .hsx file, not this one
import { state } from 'hydra';

export function Counter({ start = 0 }: CounterProps) {
  let [count, set_count] = state(start);
  return (
    <div className="counter">
      <h2>{`Value: ${count}`}</h2>
      <button onClick={(() => set_count((count + 1)))}>Add</button>
    </div>
  );
}

export interface CounterProps {
  start?: number;
}
```

No virtual machine, no interpreter: the output is ordinary React. The only
HydraScript-specific thing in it is the `hydra` import, and that import appears
only when the file actually calls a helper.

## Honest comparison with TSX

HydraScript is shorter for the things JSX is verbose about, and neither better
nor worse for everything else. This is the actual shape of the trade:

| Area | TSX | HydraScript | Verified how |
|---|---|---|---|
| Element nesting | Closing tags | Indentation | Read the emitted TSX |
| Multi-branch UI | Nested ternaries / IIFE switch | `if / elif / else`, `match` | Compiled both |
| Dynamic classes | `clsx(...)` import | `cls={...}` dict, no import | Emitted `cx(...)` |
| Event prevent/stop | Manual `e.preventDefault()` | `on_submit_prevent_stop=fn` | Emitted both calls |
| List rendering | `.map()` + `key` | `for x in xs:` + `key=` | Emitted `.map()` |
| String interpolation | Template literals | f-strings | Emitted template literal |
| State | `const [v, setV] = useState()` | `v, set_v = state()` | Emitted `useState` |
| Multiple roots | Manual `<>...</>` | Automatic | Emitted fragment |
| Token count for the same component | 188 tokens | 130 tokens | `benchmarks/tokens.py` |

The last row is measured on one component in the repo, not a corpus — see the
next section for exactly what is and is not claimed.

One correction worth stating because it surprises people: `count && <Badge/>`
renders `0`, not nothing. The compiler emits `count && (<span>…)` exactly like
TSX does. Use `if count:` when you want the guard.

## Syntax reference

### Indentation

`h1: "text"` puts one child inline. A trailing `:` with an indented block nests:

```python
div(className="container"):
    header(className="header"):
        h1: "System Status"
        p: "All telemetry nodes online."
```

### Multiple roots

Siblings at the top of a component wrap in a fragment automatically:

```python
component MetricPair(label: str, value: str):
    span(className="label"): label
    span(className="value"): value
```

```tsx
export function MetricPair({ label, value }: MetricPairProps) {
  return (
  <>
    <span className="label">{label}</span>
    <span className="value">{value}</span>
  </>
  );
}
```

### Props and events

`class` / `cls` → `className`, `for` → `htmlFor`, `tab_index` → `tabIndex`,
`on_click` → `onClick`, `on_change` → `onChange`, `on_submit` → `onSubmit`,
`on_key_down` → `onKeyDown`. `aria_*` and `data_*` keep their hyphens.

Suffixes add the boilerplate for you:

* `on_submit_prevent=fn` → `e.preventDefault()` then `fn(e)`
* `on_click_stop=fn` → `e.stopPropagation()` then `fn(e)`
* `on_click_prevent_stop=fn` → both

### Dynamic classes

```python
div(cls={"btn": True, "active": is_active, "muted": not is_active}): "Hi"
```

emits `className={cx({...})}` with `cx` imported from `hydra`.

## Language features

Python semantics are preserved rather than approximated. Each of these is
covered by a test in `compiler-rs/tests/compile.rs`:

```python
a = 0 < x < 10              # chained comparison
found = key in items        # membership, not property presence
same = a is b               # identity
a, b = b, a                 # parallel assignment
p = q = r = 0               # chained assignment
name, age = get_user()      # destructuring
xs[1:3] / xs[:5] / xs[::2]  # slicing
{k: v for k, v in pairs}    # dict comprehension, tuple targets too
{x for x in xs}             # set comprehension
total = 0
for x in xs:
    total += x              # augmented assignment on any target
```

`def` containing `yield` becomes a generator (`function*`). `class` with
`__init__` becomes an ES class (`this`, `@staticmethod`, inheritance).
`@deco` becomes `f = deco(f)`. `@dataclass` synthesises `__init__` from the
annotated fields.

`slot` in a component body renders `props.children` and adds `children` to the
props type:

```python
component Card(title: str):
    div(className="card"):
        h3: title
        slot
```

### Error types

`class MyError(Exception)` produces a real JS class, and `raise` keeps a usable
stack trace:

```python
class ValidationError(Exception):
    pass

def check(x):
    if x < 0:
        raise ValidationError("negative")
```

### The `.hys` side

`.hys` files compile to plain JavaScript — no React, no JSX. Useful for scripts
and Node utilities:

```python
from "node:fs/promises" import readFile

async def count_lines(path: str):
    raw = await readFile(path, "utf8")
    return len(raw.split("\n"))
```

Run one directly with `hydra run script.hys`.

## Runtime (`hydra`)

Both the compiler's helpers and the React adapters come from a single
specifier, `hydra`, which resolves to `runtime/hydra.ts`.

**Three specifiers, and the compiler enforces which one you may use where:**

| import from | holds | allowed in |
|---|---|---|
| `hydra` | universal helpers (`state`, `fetch_json`, `mount`, `Router`) | any module |
| `hydra/server` | `env`, `read_text`, `write_text`, `redirect`, `action_flow` | a `.server.hys` only |
| `hydra/client` | `window_size`, `scroll_to`, `local_storage`, `clipboard` | a `.hyx`/`.tsx` only |

Importing `hydra/server` from a page is a **build error that names the file and
says why**, not a stack trace at run time:

```
[hydra] src/pages/index.hyx imports "hydra/server".
        A page is bundled for the browser, so a server-only module cannot be
        reached from it. Move the code into src/pages/index.server.hys and read
        the value from a loader instead.
```

The reverse is checked too: `hydra/client` in a `.server.hys` fails, because
there is no `window` there. This is the compiler refusing an import it can prove
is wrong, which is the only kind of import it refuses.

| Function | React API |
|---|---|
| `v, set_v = state(init)` | `useState` |
| `r = ref(init)` | `useRef` |
| `cb = callback(fn, deps)` | `useCallback` |
| `effect(fn, deps)` | `useEffect` |
| `v, toggle_fn, set_v = toggle(False)` | custom (3-tuple, not 2) |
| `is_mounted = use_mounted()` | custom |

The runtime also exports ~150 smaller helpers (`debounce`, `fetch_json`, `cx`,
`get_path`, `use_dark_mode`, …). `hydra doctor` and `hydra list` are the quickest
way to see what a project actually has.

**Do not name your own runtime file `src/hydra.hys`.** The specifier `hydra` is
the compiler's contract; a project file cannot satisfy every helper the compiler
can emit, and shadowing it fails with `No matching export in src/hydra.hys for
import len_of`. Import project code by relative path.

## Built-in functions

These need no import:

| HydraScript | Emits |
|---|---|
| `len(xs)` / `len(d)` | `xs.length` / dict-aware `len_of(d)` |
| `max(a, b)` / `max(xs)` | `Math.max(a, b)` / runtime `max_of(xs)` |
| `min(a, b)` / `min(xs)` | `Math.min(a, b)` / runtime `min_of(xs)` |
| `abs(x)` / `round(x)` | `Math.abs` / runtime `round_py(x)` — tie to even |
| `pow(a, b)` | `a ** b` |
| `sum(xs)` / `sum(xs, start)` | reduce / runtime helper |
| `sorted(xs)` / `reversed(xs)` | non-mutating; numbers compare numerically |
| `str` / `int` / `float` / `bool` | `String` / runtime `int` / `float` / `truthy` |
| `isinstance(x, int)` | `isinstance(x, Number)` |
| `type(x).__name__` | `x.constructor.name` |
| `enumerate` / `range` / `zip` | runtime helpers, auto-imported |
| `xs.some(lambda x: x > 2)` | `xs.some((x) => x > 2)` |
| `print(x)` | `console.log(x)` |
| `assert cond, "msg"` | `assert_(cond, "msg")` — throws |
| `raise ValueError("x")` | `raise_(new ValueError("x"))` |

Python string methods with no JS equivalent (`s.capitalize()`, `s.zfill(4)`,
`s.isdigit()`) and collection helpers (`", ".join(xs)`, `d.get(k, v)`,
`xs.extend(ys)`) call into the runtime. The import is injected for you. Helpers
delegate to a receiver that owns the equivalent method, so `.add()` / `.remove()`
stay safe on non-list objects like `DOMTokenList`.

### Constructors

Python has no `new`; browser APIs need it, so it is part of the language:

```python
def setup():
    obs = new IntersectionObserver(on_change, {"threshold": 0.25})
    obs.observe(el)
    return obs
```

`fn?.(x)` compiles to an optional call.

### Module imports

```python
from "react" import useState, useEffect   # named import
from "./Header.hyx" import Header         # local component
import "./index.css"                      # side-effect
from "./logo.svg" import logo             # asset: default import
export component Button(label: str):      # exported component
    button: label
export def tax(amount):                   # exported function
    return amount * 0.11
```

## Components and JSX output

A `component` becomes an exported React function component with a matching
`Props` interface. Prop defaults map to destructuring defaults. `self` is `this`,
`__init__` is the constructor, and `super().__init__(x)` becomes `super(x)`.

Output validation: every emit is checked before it leaves the compiler
(`src/validate.rs`). It rejects shapes that are always invalid JavaScript — a
declaration whose target is a member expression, `new` with nothing to
construct, unbalanced brackets in plain-JS output. A failure here is a compiler
bug and the message says so. This exists because the compiler once reported
success for output no JS engine would accept.

## Meta-framework

`hydra dev`, `hydra build` and `hydra preview` are the whole framework. They use
esbuild directly — there is no `vite.config.ts`, and nothing needs one.

| Command | Does |
|---|---|
| `hydra dev` | Build, serve, rebuild on change, live-reload the browser |
| `hydra build` | Production bundle into `dist/`, pre-render static routes, run the runtime gate |
| `hydra preview` | Serve a finished `dist/` exactly as a host would |

A page is a file. `src/pages/about.hyx` is `/about`; `src/pages/blog/[slug].hyx`
is `/blog/:slug`; `_layout.hyx`, `_404.hyx` and `_error.hyx` are picked up at
every level.

```python
# src/pages/blog/[slug].hyx
component Page(props):
    article():
        h1(): props["post"]["title"]
        p(): props["post"]["body"]
```

```python
# src/pages/blog/[slug].server.hys — runs on the server, never shipped
def loader(ctx):
    return {"post": find_post(ctx["params"]["slug"])}

def static_params():
    return [{"slug": s} for s in all_slugs()]
```

Data reaches a page through `loader`; a form calls an `action`; `src/api/*.hys`
are JSON endpoints; `src/middleware.hys` runs before both. `.env` is loaded, and
only names starting with `PUBLIC_` may be read from browser code — a build that
tries otherwise fails and names the variable.

`hydra build --target static` drops the server half and prints exactly what it
dropped. `--target node` keeps it.

**[Read the guide](docs/GUIDE.md)** for the full behaviour: routing rules,
pre-rendering per route, metadata, actions and redirects, API route shapes,
middleware ordering, the `PUBLIC_` split, deployment targets, SSR for dynamic
routes, `hydra test` and `hydra lsp`.


## Configuration

A single optional `hydraconfig.json` in the project root:

```json
{
  "name": "production-app",
  "root": "./src",
  "outputDir": "./dist",
  "base": "/",
  "server": {
    "port": 5173,
    "host": "127.0.0.1",
    "proxy": { "/api": "http://127.0.0.1:8000" }
  },
  "compiler": {
    "target": "react-18",
    "strict": true
  },
  "rendering": { "ssg": true },
  "tailwind": {
    "theme": {
      "extend": {
        "colors": { "primary": "#f54e00" }
      }
    }
  }
}
```

`base` also handles subpath deployment: with `"/sub/"`, HTML, chunks and assets
all reference `/sub/`, and `hydra preview` serves them there. `server.proxy`
forwards during dev and preview, keeping the prefix intact.

Environment variables: `HYDRA_NATIVE` (addon path), `HYDRA_COMPILER` (CLI path),
`HYDRA_RUNNER` (runner path), `HYDRA_RUNTIME_PATH` (what `hydra` resolves to).

### `hydra init`: what to generate

Run it in a terminal and it asks; run it in a pipe or CI and it takes the
defaults, so existing scripts keep working.

```
$ hydra init my-app

  Template
  ❯ 1. App — routing by file, several pages (recommended)
    2. Blank — one page, one component, no router

  Styling
  ❯ 1. Tailwind — utility classes, configured in hydraconfig.json
    2. PostCSS — your own plugin list, no Tailwind
    3. Plain CSS — no transform step at all

  Layout
  ❯ 1. Pages — one file per URL under src/pages (recommended)
    2. Single — one page, no file-based router

  Pre-render pages at build time (SSG)? [Y/n]:
  Generate TypeScript declarations (.d.ts)? [Y/n]:
```

Enter accepts the default, so the whole thing is four keystrokes. Every answer
can also be given as a flag, which is what CI wants:

```bash
hydra init my-app --template=blank --styling=plain --ssg=false --types=false
hydra init my-app --yes                      # defaults, no prompts
```

| Flag | Values | Default |
| --- | --- | --- |
| `--template=` | `app`, `blank` | `app` |
| `--styling=` (alias `--css=`) | `tailwind`, `postcss`, `plain` | `tailwind` |
| `--layout=` | `pages`, `single` | `pages` |
| `--ssg=` | `true`, `false` | `true` |
| `--types=` | `true`, `false` | `true` |
| `--yes`, `-y` | — | prompts only when a terminal is attached |

The answer changes what is written, not just a comment: `--styling=plain` omits
`tailwind.config.js`, leaves `tailwindcss`/`postcss`/`autoprefixer` out of
`package.json`, and writes `src/index.css` with the classes the generated page
actually uses. `--template=blank` writes a single `src/App.hyx` and no
`src/pages` folder.

An unknown value is an error (`--styling=twind` exits 2 and writes nothing)
rather than being ignored, because scaffolding Tailwind after someone asked for
something else is the failure that wastes the most time.

Run `hydra doctor` first when a build misbehaves — it reports node, npm, bun,
config discovery and source counts. `hydra watch` writes to `watch-out/`,
mirroring `src/`, never next to the sources it reads.

### Using HydraScript from TypeScript

`.hyx` modules are visible to TypeScript, so a mixed project type-checks across
the boundary. Generate the declarations once, and again whenever a component's
parameters change:

```bash
npx hydra types        # writes src/Widget.hyx.d.ts next to src/Widget.hyx
```

The filename is the contract: TypeScript looks for `<file>.hyx.d.ts` beside
`<file>.hyx`. A sibling `Widget.d.ts` is ignored.

```tsx
import { Widget } from './Widget.hyx'

// `label` is a string and `size` is an optional number, straight from the
// component's own parameters. A typo is an error, not a silent `any`:
<Widget label="hi" size={2} />
```

Rules the generator follows, because a declaration that lies is worse than none:

- Prop types come from the component's parameters, mapped from Python names
  (`int`/`float` -> `number`, `str` -> `string`, `list` -> `any[]`). An
  unannotated parameter becomes `any`, never a guess.
- A construct it cannot represent is omitted rather than approximated: a class
  gets a permissive index signature, not invented members.
- A module with no exports produces no file, so a hand-written `.d.ts` is never
  clobbered.

A `declare module '*.hyx'` shim is the tempting five-minute alternative. It makes
every import `any` and silently switches off type checking at exactly the
boundary you wanted checked, so prefer `hydra types`.

## Installation

```bash
# As a dev dependency in a project
npm install -D hydrascript

# Or globally, to get the `hydra` command anywhere
npm install -g hydrascript

# Run it once without installing
npx hydrascript init myapp
```

The package is on the npm registry; the names differ, and that is deliberate.
The **package** is `hydrascript`, the **command** is `hydra`. So `npx hydrascript`
installs the package and runs the `hydra` binary inside it. There is an unrelated
package already called `hydra` on the registry, so `npx hydra` without a local
install would fetch that one instead — always go through `hydrascript`.

To pin a specific commit instead of the released version:

```bash
npm install -D hydrascript@github:hanxthvy/hydrascript#<sha>
```

The npm package ships a prebuilt compiler for every platform npm can run on.
Nothing is compiled on install, and no Rust toolchain is needed to use it:

| Target | Package installed | In-process addon |
|---|---|---|
| Linux x64 (glibc) | `@hydrascript/linux-x64` | yes |
| Linux arm64 (glibc) | `@hydrascript/linux-arm64` | yes |
| Linux x64 (musl / Alpine) | `@hydrascript/linux-x64-musl` | no |
| Linux arm64 (musl) | `@hydrascript/linux-arm64-musl` | no |
| macOS Intel | `@hydrascript/darwin-x64` | yes |
| macOS Apple silicon | `@hydrascript/darwin-arm64` | yes |
| Windows x64 | `@hydrascript/win32-x64` | yes |

These are `optionalDependencies` of `hydrascript`, so npm installs exactly the one
that matches the machine and skips the rest. The addon is the in-process compiler
(`bin/hydra.node`); without it — the two musl targets — the CLI is spawned per
file instead, which works everywhere and is the difference between 0.025 ms and
~7 ms per compile in `vite dev`, not between working and not working.

If a platform is missing from that table, `bin/hydra.js` fails with the triple it
wanted and the two ways out, rather than a loader error that names nothing. To
build from source anyway:

```bash
git clone https://github.com/hanxthvy/hydrascript.git
cd hydrascript/compiler-rs
cargo build --release
cp target/release/hydra ../bin/hydra
cp target/release/libhydra.so ../bin/hydra.node
```

Requirements: Node 22+ (`engines` enforces it; the runner uses the global
`WebSocket`), Rust 1.75+ (edition 2021) to build the compiler.
`npm install` brings esbuild, which is the one thing a build cannot do without.
PostCSS, Tailwind and Autoprefixer are **not** installed by the framework: a
project that wants them installs them, exactly like any other tool. See
[Styling](#styling).

## Styling

The CSS pipeline belongs to the project. There is no framework-imposed default,
and `tailwindcss` is not a dependency of `hydrascript` — install it only if you
want it.

`src/index.css` is processed by whichever of these matches first, most explicit
winning:

| Your project has | What runs |
|---|---|
| `postcss.config.{js,mjs,cjs,ts}` or `.postcssrc*` | that config, plugins and all |
| `"styling": ["autoprefixer", "./my-plugin.mjs"]` in `hydraconfig.json` | exactly those plugins |
| a top-level `tailwind` key, or a `tailwind.config.*` file | Tailwind + Autoprefixer |
| none of the above | plain PostCSS; Autoprefixer only if installed |

The build prints which one ran, so a stylesheet that comes out wrong has an
answer in the log:

```
[hydra] styling: tailwind (tailwind.config.js)
[hydra] styling: plain postcss
[hydra] styling: plugins (autoprefixer)
```

**Tailwind, if you want it:**

```bash
npm i -D tailwindcss postcss autoprefixer
```

```json
// hydraconfig.json
{ "tailwind": { "theme": { "extend": {} } } }
```

```css
/* src/index.css */
@tailwind base;
@tailwind components;
@tailwind utilities;
```

**Something else — Sass, CSS modules, a custom transform:** put a
`postcss.config.mjs` in the project and it is used as-is. Writing it as `.cjs`
matters when the project is `"type": "module"`, because PostCSS configs written
for CommonJS cannot be imported as ESM.

**Plain CSS, nothing extra:** write `src/index.css` and build. Without PostCSS
installed the file is copied unprocessed rather than dropped, and the build says
so.

The three CSS packages are optional peers, resolved from **your** `node_modules`
only. The framework will not silently use its own copy — a project that never
installed Tailwind gets a message naming the install command, not a stylesheet
that quietly came out of a framework dependency.

## Editor support

Two ways to get editing support, and they are different things:

- **`editors/vscode`** — syntax highlighting plus inline diagnostics. It runs
  `hydra check --json -` and turns the JSON into squiggles, so it reports every
  finding, not only the first. Copy or symlink it into
  `~/.vscode/extensions/hydrascript` and reload.
- **`hydra lsp`** — a real language server, for an editor that speaks LSP:
  diagnostics, hover, go-to-definition, and rename within one file.

Configure the LSP in VS Code with the `vscode-languageclient` extension of your
choice, or in any editor that accepts an LSP command:

```json
{ "command": "hydra", "args": ["lsp"] }
```

The extension does NOT start the server for you: the two overlap on diagnostics
and wiring both would double every squiggle.

## When something fails

Four things can go wrong at run time rather than at build time, and each one has
a defined answer. This section exists because "why is my page empty" is the
question that costs a developer an afternoon, and the answer should be in the
response, not in a terminal they may not have open.

### A loader throws

The route is still served, and the response says what happened, naming the file
the author actually edits:

```
HTTP 500
hydra: the server could not render /blog/x

loader for /blog/:slug (blog/[slug].server.hys) threw: Cannot read properties
of null (reading 'missing')

TypeError: Cannot read properties of null (reading 'missing')
    at loader (...)
```

The `.hys` path and the pattern are in there because the raw stack is not
actionable on its own: it points into a built server bundle the author has never
opened. The terminal gets the same message, one line.

`GET /__hydra/data` answers `500` with `{"error": "..."}` for the same failure,
so a client-side navigation reports it too. It is **never** an empty data object:
`[]` and "the request failed" look identical in a UI and mean different things.

### A component throws while rendering

React catches it with the route's error boundary (`_error.hyx` for that folder),
which is what renders the failure. If the render throws before React can, the
server writes the same notice into the shell and answers `500` — a blank page
with a `200` and no explanation is what this avoids.

### A page renders nothing

Not fatal, and reported by the build as a warning, because a page legitimately
rendering nothing until a fetch resolves is a real pattern:

```
warning: /about/ — root rendered nothing (#root has no children and the body has no text)
```

The build prints it; the runtime gate distinguishes it from an exception. If you
see it and did not expect it, the component returned nothing — a missing `return`
is the usual cause, and `hydra check` will not catch it because the name is
bound.

### Hydration mismatch

A mismatch is a **build failure**, not a console warning: the runtime gate loads
every HTML file the build wrote and fails on an uncaught exception, and React
reports a mismatch by throwing (#418 / #423 / #425). The usual causes are an
inlined payload for a different URL, or a component reading `window` during the
first render. Both are fixed in the framework; if you hit one, it is a bug worth
reporting rather than a caveat worth working around.

## Permanent limitations

Design decisions that will not change. Each one is a choice, and the reason is
here so it can be argued with rather than guessed at.

- **No multiple inheritance.** A second base would have to be emulated, and every
  emulation differs from Python somewhere the author cannot see: which base wins
  in a diamond, whether `super()` follows the MRO, what `isinstance(x, Both)`
  answers. Refused by name at parse time, on both targets.
- **Keyword arguments only where a signature can be read.** A function defined in
  the file, a function imported from a RELATIVE `.hys`/`.hyx` file, and a method
  whose name only one class in the file declares. A call into a package has no
  source to read; a method whose name two classes declare needs the receiver's
  type, which is not tracked. Both are compile errors, never silent miscompiles.
- **Builtins with no exact JS equivalent keep their differences, stated not
  hidden.** `any` / `all` short-circuit and answer the empty-sequence cases the
  way Python does (`any([])` is `False`, `all([])` is `True`). `getattr(x, "y")`
  with no default raises `AttributeError` rather than returning `undefined`,
  which is what makes the three-argument form mean anything. `repr` is JSON for
  plain data and `String(x)` elsewhere, because a JS object has no `__repr__`.
- **The Linux binaries need glibc 2.35+; use the musl build otherwise.** The
  glibc floor is Ubuntu 22.04, because that is the runner the release is built
  on: a binary linked against a newer glibc refuses to *start* on an older
  system, which is how 0.7.0 shipped a tarball whose `hydra build` worked (it
  runs the Node runner) while `hydra run` and `hydra check` died with "weak
  version `GLIBC_2.39' not found". The release workflow fails if a binary
  requires a glibc newer than the runner it was built on, and the two musl
  targets exist for exactly the systems that cannot meet the floor.
- **The two musl targets ship no in-process addon.** Cargo refuses a `cdylib`
  for those targets, so `bin/hydra.node` is absent there and the compiler runs as
  a subprocess. Correct everywhere, slower per compile in `vite dev`.
- **Rounding is Python's, to the tie.** `format(1.5, ".0f")` is `2` and
  `format(0.5, ".0f")` is `0`: ties go to the even digit, judged against the
  value's exact binary expansion. `toFixed` rounds ties away from zero, which is
  a different answer on money and percentages, so it is not used for a
  `f`/`F`/`e`/`E` spec. The tie is detected after expanding the double to 100
  fraction digits; beyond `1e-100` the difference is under any precision an
  f-string can express, which is a bound rather than a guess.

### Streaming, precisely

The row above says shipped, and it is, with the limit stated where the claim is
made rather than in a footnote. `renderPageStream` writes the document head
immediately and pipes React's output as it is produced, so a page with a slow
boundary is not a blank document for the duration of that boundary. The test
asserts on socket chunks, not on content, because a buffered renderer produces a
correct document and passes every content assertion — the difference is only
visible in when the bytes arrive.

What does **not** stream is the route's own loader. It is awaited before the first
byte, because `renderSync` needs a value to render with, and storing a pending
promise in the seed would make the render non-deterministic. Streaming the loader
itself needs a resolver-based renderer (or RSC), which this is not. So: everything
below a Suspense boundary streams, the root loader does not, and both sentences
are true at once.

### Fast Refresh, precisely

State **is** preserved and the new markup **swaps into the live tree**: the dev server
sends `refresh` with the new entry URL, the dev runner virtualizes React/ReactDOM as
shared singletons across re-imports, and the component boundary in `runtime/hydra.ts`
notifies mounted instances of the new implementation.

This is measured end-to-end — `scripts/fast-refresh-probe.mjs` drives a real browser,
clicks a counter to 3, edits the component on disk, and verifies that the window is
never reloaded, hook state remains at 3, and the edited button label updates in the
live DOM.

Not planned, and not a gap: React Server Components, islands and multi-platform
deploy adapters. The compiler's output is ordinary React on the client, and that
is a feature with a name rather than an unfinished one.

**Streaming SSR is real, with one limit written down.** `renderPageStream` writes
the document head immediately and pipes React's output as it is produced, so a
slow boundary does not hold a blank page. The route's own loader is still awaited
before the first byte, because the renderer needs a value; streaming the loader
itself needs a resolver-based renderer, which this is not. The test asserts on
socket chunks rather than content, because a buffered renderer produces a correct
document and passes every content assertion — the difference is only visible in
when the bytes arrive.
